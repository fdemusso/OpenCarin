# 05 — OSM against the disc: which record fields can we still not explain?

A data study, not an implementation: nothing is written to a disc and nothing is run on a unit. To build a
disc from OpenStreetMap we must know which value of each field to generate for a given OSM way. The fields
whose meaning we cannot attribute block a correct generator, so we use OSM (today's and the state at the
disc's build date) as an oracle for the **unexplained fields** of the street-tile segment record
(`docs/carindb/03-road-network.md` §6.7) and say, field by field, what is explained, what is a hint and what
is still unknown. The result is in [`CHANGES.md`](CHANGES.md), one section per field of the worklist.

The two discs are read **in place** (`dataset/NAV_DB_21708.ISO` and `NAV_DB_21734.ISO` at the repository root
are symlinks; nothing is copied). Everything this example writes goes to `dataset/` here, which is
git-ignored, **under 50 MB** (the figure is printed by `00_setup.py`), safe to delete and regenerated by
the scripts. Every script skips what exists and has `--force`.

## Steps

| Script | Does | Writes (`dataset/`) |
|---|---|---|
| `00_setup.py [--check-only] [--clean [--all]]` | checks uv, numpy, the discs, the Rust tool, disk space, Overpass; runs steps 1 and 2 | |
| `01_extract_disc.py` | street tiles of each area from each disc, every field of the 32-byte record, nodes, S10, S11, S12 | `disc_<disc>_<area>_{segments,nodes,turns,signs,tiles}.csv.gz` |
| `02_fetch_osm.py` | OSM highways and turn restrictions per area, today and at 2015-07-21 (Overpass attic), in cells, with retries | `osm_<area>_<now\|2015>.json.gz` |
| `03_match.py` | every disc segment to an OSM way (nearest piece within 15 m, same direction ±30°, same name preferred) | `match_<disc>_<area>_<snapshot>.csv.gz` |
| `04_form7_s10.py` | form of way 7, S10 flags 0-3 against OSM tags, context and restriction relations | |
| `05_nodes.py` | node flags (S5/S6 `+6`) against degree, level, section and segment attributes | |
| `06_speed.py` | speed category and built-up bit against `maxspeed`, `highway`, density | |
| `07_signs_tmc.py` | signposts (S11) and TMC (S12): which segments, what texts | |
| `08_sample_disc.py` | random street tiles of the whole disc, for the rare values the study areas lack | `sample_<disc>_<n>_*.csv.gz` |
| `09_disc_vs_disc.py` | the same road on 21708 (2015) and 21734 (2018): which fields change | |
| `10_bytes.py` | every byte of the record, `+0x10` bit 7, `+0x1D` bits 4-6, `+0x18`, junction 3/4, S7 flags, tile header | |

Areas (`common.py`): `bari_modugno`, `rural_a14`, `altamura` (Puglia; city, ring road and A14, small towns, open
country) and six one-tile areas `x_*` elsewhere in Europe, each chosen because the random sample found a rare
value there (junction 3 and 4, `+0x10` bit 7, `+0x1D` bits 4-6).

```bash
uv run --with numpy python examples/06_osm_vs_disc_modugno/00_setup.py            # checks, then steps 1 and 2
uv run python examples/06_osm_vs_disc_modugno/03_match.py
uv run python examples/06_osm_vs_disc_modugno/04_form7_s10.py                     # | tee dataset/report_04.txt
uv run python examples/06_osm_vs_disc_modugno/05_nodes.py
uv run python examples/06_osm_vs_disc_modugno/06_speed.py
uv run python examples/06_osm_vs_disc_modugno/07_signs_tmc.py
uv run --with numpy python examples/06_osm_vs_disc_modugno/08_sample_disc.py --n 400   # about a minute
uv run python examples/06_osm_vs_disc_modugno/09_disc_vs_disc.py
uv run python examples/06_osm_vs_disc_modugno/10_bytes.py
```

A rerun takes seconds (disc extraction: about 5 s per area; matching: seconds to a minute; the analyses:
seconds). The only slow step is the download: `overpass-api.de` is often busy, so `02_fetch_osm.py` asks one
cell of 0.07° at a time, retries with a growing pause and on mirrors, and keeps finished cells.
`00_setup.py --clean` deletes `dataset/` except the downloads (`--all` deletes those too).

## Method and limits

- **The disc is HERE/Navteq data, not OSM.** The two sources differ for reasons that have nothing to do
  with the format (digitising, classification, one-way and speed sources). The comparison measures that
  difference; a field "explained by OSM" only means the disc's value is predictable from OSM tags to the
  stated rate. Disc 21708 is compared with both snapshots of OSM and reported separately.
- **Matching.** A disc segment is *matched* when one OSM way holds at least 70% of its samples (every 8 m)
  within 15 m and within 30° of its direction. The match is the way chosen by most samples; names are
  folded (case, accents). Parallel carriageways closer than 15 m can be swapped; direction and name
  keep that rare but the rates in `CHANGES.md` are not corrected for it.
- **Evidence.** Disc data decides. A field is *explained* only if a hypothesis holds on a large sample
  (n, k and the exceptions given) and could have failed; otherwise *hint* or *unknown*. Negative results
  are recorded with numbers.
- **Not on a unit.** Nothing here is validated on a unit. Every verdict says what the data show, not what
  the firmware does with it, except where a firmware read is cited. A later firmware cross-check (disassembly of the RR modules, no script here)
  is summarised in `CHANGES.md` ("Firmware cross-check") and in `docs/fw/04-rr-rpmod-edge-record.md` §5-10.
